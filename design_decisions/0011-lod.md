# ADR-0011 — Distance-based discrete LOD with per-LOD draw batches

- **Status**: accepted
- **Date**: 2026-05-12
- **Deciders**: renderer
- **Tags**: lod, performance, phase-1.5

## Context

M14 closed GPU occlusion culling (HZB stats); M15 owns level-of-detail selection. Real scenes need to draw distant objects with lower-poly meshes so the total per-frame triangle budget stays bounded as the camera moves through wide spaces.

Three forks worth naming:

1. **Discrete LOD vs continuous (geomorph / tessellation).** Discrete LOD = pre-built mesh chain, pick one level per instance. Continuous = single mesh with per-vertex morph or hardware tessellation control. Discrete is the industry default at the AAA scale we're targeting; continuous is a feature, not a foundation.
2. **CPU selection vs GPU-driven selection.** CPU is trivial (loop over instances, compute distance, pick level). GPU lets the same compute pass that does HZB cull also emit per-LOD indirect draws. CPU is simpler and matches the M14 pattern of "GPU computes the *signal*, CPU drives the *draws*".
3. **Per-LOD batched draws vs single-draw with vertex-shader LOD branch.** Batched draws use one VBuf/IBuf per LOD and N draw calls. A single-draw variant binds all LOD mesh data through structured buffers and picks a vertex range per instance from the vertex shader. Batched is much simpler and easily portable to GPU-driven indirect later.

## Decision

- **Discrete 3-step LOD chain** for the sphere mesh: `{20,32}` → `{10,16}` → `{6,10}` (lat/lon segments). Triangle counts drop roughly 4× per step.
- **CPU distance-based LOD selection**, recomputed every frame for each of the 5 demo spheres. Override with `--force-lod {0|1|2}` for debugging.
- **Per-LOD batched draws** — the instance buffer is filled in LOD-grouped order (`[LOD0…LOD1…LOD2]`), then the shadow and G-Buffer passes loop over LODs, each pass picks the matching VBuf+IBuf and dispatches `draw_indexed(instance_count = lod_count, base_instance = lod_offset)`.
- **LOD distribution exposed in the HUD** as `LOD H<x> M<y> L<z>  TRIS A/B`, where B = baseline (all-high) and A = actual drawn. Validates the system at a glance.

The RT side (BLAS for sphere) still uses the **high-LOD mesh exclusively**. Reflections always sample the most detailed geometry; rasterization picks LOD per camera distance. This avoids per-LOD BLAS bookkeeping in M15 v1 — TLAS scope is already documented as static (P1-RT-STATIC-TLAS-001).

## Alternatives considered

1. **Single VBuf with all LODs concatenated + per-instance vertex range.** Pros: one draw call, no rebinding. Cons: needs the vertex shader to know the LOD's vertex/index range, which means either a structured buffer or per-instance push constants — both more API surface than the existing `base_instance` mechanism. **Rejected** for v1.

2. **GPU-driven LOD via the M14 HZB cull compute.** Pros: a single compute pass produces visibility + LOD + indirect draw arguments. Cons: requires `MTLIndirectCommandBuffer` (separate ADR, tracked in TECH_DEBT as part of the M14.b plan). **Deferred.**

3. **Continuous LOD (tessellation / geomorph).** Pros: no popping. Cons: massive feature surface; geomorph wants a custom mesh format with per-vertex collapse pairs; tessellation wants either tess-control/eval stages or compute-driven mesh shading. **Rejected for Phase 1.5.**

4. **Per-LOD BLAS for RT.** Would let reflections sample the same LOD the camera sees. Cons: TLAS rebuild whenever LOD assignments change, or per-frame TLAS refit which we don't have yet. **Deferred** with the static-TLAS work (P1-RT-STATIC-TLAS-001).

## Consequences

**Easy now:**
- LOD0/1/2 meshes are real RHI resources owned by the renderer; new objects can opt in by adding their own LOD chains.
- The instance-buffer-packing trick (LOD-grouped order) gives free batching for any future mesh that needs LOD.
- HUD shows real triangle savings — useful for perf budgeting demos.

**Committed:**
- One VBuf+IBuf per LOD per mesh — modest memory bump per asset.
- The CPU pays the LOD-selection cost. With ~5 spheres it's trivial; with thousands of dynamic objects we'd want SIMD or GPU-side selection.

**Explicitly not committing to:**
- Per-LOD BLAS for RT (deferred).
- Continuous LOD (out of scope).
- LOD bias from screen-space size (using projected radius instead of raw distance) — distance is fine for our scene, but a real engine would use screen size to be field-of-view-aware.

## Tradeoffs

- **Memory**: +2 sphere meshes (~720 verts and ~270 verts on top of the 640 of LOD0). Negligible.
- **CPU**: O(N_spheres) distance check per frame. <1 µs for the demo.
- **Draw calls**: spheres now generate up to 3 draws instead of 1. With 5 spheres distributed across 3 LODs the cost is dominated by state changes, which Metal handles efficiently.
- **GPU**: total triangles drawn drops to whatever the LOD distribution sums to. Visible savings only when the scene actually spans many distance buckets — the existing 5-sphere row is mostly at one distance, so use `--force-lod 2` to see all spheres on the low mesh and `--force-lod 0` for the high baseline.

## Open questions

- Screen-projected radius vs raw distance: probably the right default for any production scene. Lift when needed.
- LOD dithering / temporal blending to hide popping: a Phase 2 visual-polish item.
- Asset pipeline: M16+ will load real glTF meshes that may ship their own LOD chains. We need to decide whether the LOD chain is per-asset (loaded from the file) or auto-derived (decimation post-process).

- `examples/hello_metal/main.cpp` —
